# 拾光小册 · 发布链路（唯一允许的路径）

> **2026-10-25 用户定规**：「我需要你以后只能走正确链路：dev 改 → dev 测 →
> build-release.ps1 打包 → deploy.ps1 部署（自动写部署记录）。如何设置，
> 确保以后只能走这条路？」
>
> 本文说明这条纪律**由哪些机械闸门保证**，以及各自拦在哪一步。

---

## 一、唯一允许的链路

```
① dev 改        <开发仓库目录>\src\…          ← 代码真源，git 仓库
② dev 测        node tools\lint.mjs
                node tests\run.mjs fixture            ← 零依赖，秒级
                node tests\run.mjs quick              ← 发版前完整门禁（要 exe，会重启壳）
③ 升版本        VERSION.json  version → YYYY.MM.DD.NN
④ 提交          git add -A && git commit
⑤ 打包          powershell -File scripts\build-release.ps1
⑥ 部署          powershell -File scripts\deploy.ps1 -Zip release\GlimmerNote-<ver>-win-x64.zip
                  └─ 自动写 部署记录.txt + _deploy-manifest.json
⑦ 校验          node scripts\verify-deploy.mjs
```

**为什么必须先 commit 再打包**：`build-release.ps1` 把构建时间戳钉在 git HEAD
的提交时间上。未提交就打包，包里有新代码、时间戳却是旧提交 ⇒ 事后无法用 tag
复现这个包，"包 ↔ 提交"的对应关系断掉。

## 二、机械闸门（哪几条真的是机械的）

> ⚠ 这一节原来写「四层机械闸门（**不依赖任何人的自觉**）」——**那句话是错的夸张**。
> 下面把"机械拦得住"和"只靠纪律"分开写；分不清这两者，安全网就会在需要它的那天短路。

**真的机械（拦住就必须改做法，绕不过）**：

| # | 闸门 | 拦的是什么 | 位置 |
|---|---|---|---|
| 1 | **工具闸门 · 文件** | 直接 `edit`/`write` 运行区 `app\` 下任何文件 | `~/.dsh/plugins/dsh-tool-guards/rules.json` → `GN-runtime-write-via-deploy-only` |
| 2 | **工具闸门 · Shell** | 用 `Copy-Item`/`robocopy`/node 脚本等把文件塞进运行区 | 同上 → `GN-runtime-shell-copy-bypass` |
| 3 | **打包前干净树** | 工作区有未提交改动就打包 | `scripts\build-release.ps1` 第 0a 段 |
| 4 | **部署一致性** | 运行区与部署清单逐字节比对，漂移即报 | `scripts\verify-deploy.mjs`，挂 `.githooks\pre-commit` ③ |
| 5 | **提交前门禁** | `lint` 不过 / `fixture` 不过 / 运行区漂移 ⇒ 提交被拒 | `.githooks\pre-commit`（版本化真源；`scripts\install-hooks.ps1` 挂上） |
| 6 | **提交信息格式** | 非 `type(scope): subject` 或首行 >72 字符 ⇒ 提交被拒；顺带**剥掉 UTF-8 BOM** | `.githooks\commit-msg` |
| 7 | **强推 main** | 对 `refs/heads/main` 的非快进推送 | `.githooks\pre-push` |

**闸门 1/2 的豁免**（仅这三个可以碰运行区）：
`scripts\deploy.ps1`（部署）、`scripts\rollback.ps1`（回滚）、`scripts\verify-deploy.mjs`（只读校验）。
只读诊断请用 `read` 工具或 `verify-deploy.mjs --json`。

**不是机械闸门的（别把纪律当安全网）**：

| 事项 | 为什么拦不住 | 现在的替代措施 |
|---|---|---|
| `git reset --hard` / `git checkout -- <file>` | git 的钩子体系**不覆盖这两个命令**（它们不触发任何钩子），本地无法拦 | 文档纪律（`CONTRIBUTING.md §三/§四`）+ **托管平台的分支保护**（发布后开启，见 `docs\治理与架构.md §三 N1`）。**在这之前，这条铁律 100% 靠自觉。** |
| 手工改运行区后不提交 | 工具闸门能拦"改"这一动作，拦不住"用别的工具改" | 运行区漂移在每次提交、每次部署时都会被 `verify-deploy.mjs` 抓到 |

> 第 5/6/7 条是版本化的（`.githooks\`），**但新克隆必须先跑一次 `scripts\install-hooks.ps1`**——
> `.git/hooks/` 天生不入库，"开发机上有钩子"不等于"克隆里有钩子"。这条曾是本轮审计的一个 L1 阻断项。

### 为什么要两份清单/记录

- `部署记录.txt` —— 给人看：时间 / 版本 / 来源包 / 说明（历史沿革）
- `_deploy-manifest.json` —— 给机器验：逐文件 sha256 + 版本 + 包名 + 时间

后者是"运行区是否被绕过部署改动"的**唯一证据**。它由 `deploy.ps1` 独家写入，
放在运行区根目录（不是 `app\` 内），所以下次部署清空 `app\` 不会把它删掉。

## 三、常见问题

**Q：紧急修一个小 bug，能不能直接改运行区？**
不能。走完整链路，最慢也就几分钟（`fixture` 自检秒级、打包约 1 分钟）。
绕过部署的代价是：运行区出现一套不对应任何发布包的代码，事后无从追溯——
2026-10-25 就是这么坏过一次。

**Q：闸门拦了但确认是误拦怎么办？**
让人修改 `rules.json`（它 mtime 热读，改完立即生效），**不要**换另一种写法反复尝试。
每次拦截都记在 `~/.dsh/audits/tool-guards.jsonl`。

**Q：`verify-deploy` 报 exit 3？**
`3` = **这台机器根本没有运行区**（默认路径 `<仓库上一级>\GlimmerNote` 不存在）——**干净克隆就是这个状态**。
它与"漂移"（`1`）是两件事：**无法评估 ≠ 有漂移**。
`pre-commit` ③ 因此只把 `3` 降级为**可见告警**（打印 stderr + 说明）后放行；其余非 0 一律拦提交。

**Q：`verify-deploy` 报 exit 4（清单损坏）？**
说明 `_deploy-manifest.json` **读不懂**（被截断/形状不对/files 字典缺失）——运行区在、基线坏了。
这是 **fail-closed**：按阻断处理，**不许**用"删掉清单"让它变成 3（那等于把闸门拆了）。
修法：重跑一次正规部署（`build-release.ps1` → `deploy.ps1`）重建基线，再核对 `git status` 有没有人手工改过 `app\`。

**Q：`verify-deploy` 报 exit 5（尚无清单）？**
说明运行区是在建立本机制**之前**部署的历史状态。走一次正规链路即可建立基线。
**严禁**手工补一份清单——那等于自证清白，闸门就废了。

**退出码全表**（`scripts\verify-deploy.mjs` 头部注释是权威真源，此处只作索引）：
`0` 一致 · `1` 漂移（拦提交）· `2` 用法/参数错误（拦）· `3` 没有运行区（**唯一可豁免**）·
`4` 清单损坏/读不懂（拦，fail-closed）· `5` 运行区在但尚无清单（拦）。

> **2026-10-31 变更（外部审查 E03）**：改前 `2` 同时表示"没有运行区"与"清单损坏"，两个调用方
> （`tests\run.mjs`、`.githooks\pre-commit`）一律当"没有运行区"放行 ⇒ **清单损坏 = fail-open**
> （实测：把清单截断后 `pre-commit` 仍允许提交）。现在码表拆开、判据收敛到
> `tests\_测试环境.cjs` 的 `classifyVerifyDeploy()` 一处，两个调用方都按它分支，只豁免 `3`。
> 连带行为变更：`5`（尚无清单）从"告警放行"改为"拦"——**首次建立基线的机器会被拦一次**，
> 那是刻意的（建立基线只有正规部署这一条路）。
本机有运行区时，跑一次 `node scripts\verify-deploy.mjs` 就能真验证。

**退出码全表**（`scripts\verify-deploy.mjs` 头部注释是权威真源，此处只作索引）：
`0` 一致 · `1` 漂移（拦提交）· `2` 环境/用法错误（告警放行）· `3` 尚无清单（告警放行）。

**Q：真的要跳过检查提交？**
`git commit --no-verify` 可以，但 git 会记录这次跳过；且工具闸门（1/2）不归 git 管，
仍然有效。

## 四、出问题时的回滚

```
powershell -File scripts\rollback.ps1 -Version <版本>     # 从 _releases 重装归档包
powershell -File scripts\rollback.ps1                     # 不带参数 = 退回上一版
```

回滚不依赖"上一版备份目录"是否完好：`_releases\` 里保留所有发布包 + `.sha256`。
当前版本的备份在 `_app-上一版\`（`deploy.ps1` 每次部署前自动生成）。

**回滚耗时与上限**见 `docs\回退演练记录.md`（由 `selftest-pipeline.ps1` 每次演练自动追加一行；
超上限脚本会以 `exit 3` 报出来）。**别把耗时数字手抄进文档**——本文件曾因此失效过一次
（旧记录 0.3~0.8 s 来自 0.6 MB 包时代，实测已是 3.9 s）。
