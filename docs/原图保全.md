# 原图保全（内部契约）

> 立：2026-10-31（外部评审两路驱动的整改）
> 对应铁律（用户明示）：**数据方面原图是最重要、也是唯一不可复现的数据。它是核心。**

本文只写**不可从代码推断**的规则：什么算原图、身份怎么定、什么能删什么不能删、备份的分母是什么。
实现见 `src\tools\_原图.mjs`（保全库）与 `src\tools\_影像备份.mjs`（备份）。
（2026-11-01：离机镜像功能按用户决策整体移除——不做异盘镜像，备份即本机同盘副本。）

---

## 一、三个身份，不能混

| 身份 | 是什么 | 怎么定 | 能不能删 |
|---|---|---|---|
| **原图** | 整页试卷/作业照片、导入原件、收件箱里的来源映射与人工判读 | sha256 | **永不删**。删 = 数据永久丢失 |
| **孤本派生** | 无法证明能原样重建的派生件（无 `box` 的卡片证据图、待办证据截屏、笔形样本、撤卡留档、组卷成品） | sha256 + 「不在可重建集合里」 | 按原图待遇保全 |
| **可重建派生** | `_crops\`、`tiles\`、`_work-*\`、`zzznew\` | 由原图 + 裁切参数唯一确定 | 可删，随时重算 |

### 「可重建」是一个**需要证明**的断言，不是看一个字段齐不齐

- **不许**因为卡片有 `box` 就把它的 `原卷截图.jpg` 降级为可重建。实测 442 张卡的
  `原卷截图.jpg` 与 `page` 整页**尺寸无一相同**——它其实是"整页 + 红框"裁出来的那一块，
  而源图版本、旋转、缩放、编码任一不同，重裁都得不到同一份字节。`boxOk()`
  只校验"是 4 个 0~1 的数"，它**不能证明可重建**。
- **不许**因为文件在 `组卷\` 目录里就宣布可重建。那是给人看的成品。
- 要降级，唯一可接受的证据是：**在不覆盖原证据的前提下真的重建一次，并核对结果等价**。

---

## 二、身份 = 内容哈希，路径只是提示

这不是理论洁癖，有两次实测：

1. 台账里同一张照片同时出现「收件箱原名」与「原卷库改名后」两套路径（sha 相同）。
   2026-10-31 那轮只认路径的判据在 256 张里漏判 4 张，用户当场复报"这些照片我们都处理过了呀"。
2. `_页码映射.json` 的 `en` 段有 7 条指向**根本不存在的**
   `九年级/英语/原卷/课课练9上-p{24,27,31,36,39,47,48}-src{77,80,84,89,92,100,101}.jpg`——
   真实字节还躺在收件箱里叫 `pNN-srcNN.jpg`，从未改名。

**所以：任何"这张图是不是同一张"的判断，必须比字节；拿路径字符串认亲一律视为缺陷。**

## 三、保全库：`数据\_原图\`

```
_原图\<sha256 前 2 位小写>\<sha256 小写>.<原扩展名>
_原图台账.json            （在库根，不在 _原图 里面）
_原图\_快照\<时间戳>.list
```

### 三条不变量（违反即报错退出，绝不"猜一个分支继续跑"）

1. **只增不改**：目标已存在但内容不同 ⇒ **报错停止，绝不覆盖**。
   这不是"哈希碰撞才可能发生"的边角情况：磁盘位损坏、同步盘回滚都会造成它。
2. **永不删除源文件**。`入库` 只复制。清理是另一件事，必须单独批准。
3. **落盘后逐字节复核**：写完立刻重读目标算 sha256，对不上就删掉目标并报错、保留源文件。
   （源文件可能在"算哈希"与"复制"之间被改名/覆盖，只有事后复核能发现。）

### 扩展名必须保留原格式

`a.png` 存成 `<sha>.png`，绝不改成 `.jpg`。改扩展名冒充转换 = 声称"保留了原件字节"而实际转码了。

### 幂等与续跑

重复入库同一个文件 = 什么都不做（返回 `exists`）。中断后直接重跑，不会重复占空间、
不会产生半截对象（先写 `.tmp` → fsync → rename）。**入库不需要事务日志**：对象先落稳、
台账后提交，中断最多留下可识别的未登记对象（`校验` 会以"孤儿"列出，不自动删）。

### 台账自身也是真源：走 `_备份-真源\` 轮转（keep=8）

`_原图台账.json` 记的 `sources` / `names`（**哪条路径是哪个对象**）**扫 `_原图\` 复原不出来**
—— 内容寻址只保证能复原对象本身（文件名就是 sha）。而"路径 → 对象"正是
`_原图寻址.mjs` 兜底寻址的另一半（真库实测 460 条卡靠它从保全库找回）。
所以它按①真源对待：写入时留 `_备份-真源\` 副本（keep=8），另有库所在仓库的 git 历史。

**但不是"每次落盘都留一份"**：一轮 `入库 --scan` 会写 20+ 次（每 50 个文件一次检查点 + 收尾一次），
每次都留会让 keep=8 被**同一轮运行**的快照灌满，反而把**入库前**那份恢复点挤掉。
口径是**每轮入库恰好一个恢复点**：收尾那次留，中间检查点不留。
（通用纪律：高频写入 + keep=N 轮转时，备份点要按**逻辑提交**定，不按每次落盘定。）

### 快照：只存清单，**不能替代字节备份**

因为不变量①，对象永不被改写 ⇒「某时刻的库」==「那一刻的 sha 清单」。
所以快照不复制字节，只写一份 40 KB 的清单，`--diff` 与**物理扫描**对照（不是与台账对照——
台账是元数据，删掉对象后台账照旧记着它）。

**但清单只能证明"丢了什么"，不能把字节变回来。** 真正的副本靠 `_影像备份\`。
拿"有清单"当"有备份"是本项目明确禁止的推理。

## 三·补、原图兜底寻址（2026-10-31 晚）

### 问题

台账记的是**路径字符串**。路径会被改名、被搬、**被清空**（收件箱一清就是）。
一旦路径失效，卡片就打不开整页原卷了 —— 而字节明明还在保全库里。

### 解法：路径只是提示，哈希才是身份

新增 `src\tools\_原图寻址.mjs`（**只读**），提供"路径 ⇄ 身份"互查：

| 情况 | 处理 |
|---|---|
| 原路径还在 | 直接用（**零 IO**，行为与从前完全一致） |
| 原路径没了 | 用 `_原图台账.json` 的 `sources` 反查表把路径换成 sha，再从 `_原图\` 找**字节完全相同**的那一份 |
| 都没有 | `null` —— 如实报"真的断了"，**不许静默** |

反查表覆盖实测：台账里 114 条指向收件箱的 `page`、346 条 `import`，**114/114 与 346/346 全部命中**。

### 谁用它

| 消费方 | 行为 |
|---|---|
| `生成状态.mjs` | `origPage` / `origImport` 解析成**当前真正可用**的路径；多两个字段 `origResolve` / `origImportResolve`（`direct` / `store` / `lost`） |
| `_原卷台账.mjs 门禁` | 原路径失效时，**能按内容找回就不判红**，只记一条"已从保全库兜底"的可见提示 |

### 实测（真实库副本，收件箱 255 张照片全部清空）

| 判据 | 结果 |
|---|---|
| 门禁 | **452 卡 / 788 条引用全部兜底找回，0 错误** |
| 状态包 | **442 张有整页原卷的卡全部照常能打开整页**，0 张断链 |
| 反面（保全库里也删了） | 判红，并明说"真的断了" |
| 反面（同路径换成**内容不同**的另一份） | 判红 —— **按内容核对，不按路径猜**，不张冠李戴 |

**所以"清空收件箱"从此不再是数据手术**：原件已在保全库 + 本机备份里，卡片也不会断链。

### 边界（不许含糊）

- 兜底**只增不改**：它不改台账、不改路径、不删任何文件。
- 判据是**按内容**确认的（重算 sha256 比对），不是按路径猜。
  路径被复用成另一个文件时不会张冠李戴（有阴性对照守着）。
- 兜底**不能替代备份**：保全库与本机备份都在本机（2026-11-01 用户决策不做异盘镜像，
  接受单机风险）——外置副本只能靠用户自己的备份习惯。

## 三·补二、备份对账：`核对 --from <备份根>`（2026-11-03）

`_影像备份.mjs --verify` 只回答"备份与源一致吗"，`校验` 只回答"库内字节对不对"。
两者都不回答那个真正决定"出事能不能救回来"的问题：
**这份备份里，是不是每一个登记对象都有、且逐字节等于台账记着的那一份？**
（同型的缺口 2026-10-12 在 JSON 真源那侧已经吃过一次：当时只有"备份目录里有文件"，没有"能还原回去"。）

```powershell
node src\tools\_原图.mjs 核对 --from <备份根>    # 备份根 = `_影像备份\` 那类目录树，或一份 `_原图\` 副本
```

判据是**三方**逐字节一致，缺一不可：**台账（分母）↔ 库内 `_原图\` ↔ 备份根**。
备份根的形态不做假设：递归扫，"文件名是 64 位 sha"的文件才算库对象（所以
`<根>\原件\_原图\…` 与直接给一份 `_原图\` 副本都认；卡目录切片叫 `题图.jpg`，不会被误收）。

| 退出码 | 含义 |
|---|---|
| 0 | 三方一致 |
| 1 | 有差异或缺失（`--json` 在退出码非 0 时**照样**给完整结果，自动化读它） |
| 2 | 用法错（没给 `--from`，或值不是一个存在的目录） |

差异逐条指名到 sha 与 `[库]/[备份]`，原因只有四类：**缺文件 / 字节不符 / 大小不符 / 多出**。

- `大小不符` 与 `字节不符` 是**两条独立判据**：前者只可能来自"与台账登记值对账"，
  后者来自"重算 sha256"。只比 size 或只信文件名的实现必然漏掉其中一条。
- `多出`（备份里有、台账不认）**也判红**：要么库里有未登记的残留对象（先看 `校验` 的孤儿清单），
  要么备份里混进了不属于本库的东西 —— 两种都要人看一眼，不能"反正用不上"就放过。
- 库内孤儿**不判红**（与 `校验` 同口径：中断残留可识别、不自动删），只作可见提示。

边界（不许含糊）：

- `核对` **只读**：不写库、不写备份根、不改台账；而且**不取写锁** ——
  取锁本身虽只写系统临时目录，但取到之后会顺带回滚未完成的事务，那是对库的写入。
- 覆盖范围只有 `_原图\` 的**库对象**。卡目录切片、原卷整页等其余备份内容归
  `_影像备份.mjs --verify`。**"核对全绿"不等于"备份全好"**，两份判据要一起看。
- 备份里"多出来"的对象**现有两个工具谁也看不见**（它们的分母都是"库内扫描"）——
  这条判据是新的覆盖，由演练用例里的正对照守住（同一现场 `_影像备份.mjs --verify` 必须报绿）。
- `核对` 的分母是 `_原图台账.json`，所以**台账自己得先有**：它不在 `_影像备份\` 的分母里
  （那只收影像与 `_原图\` 库对象），恢复点走**它自己的 `_备份-真源\` 轮转（keep=8）**＋库所在仓库的 git
  （口径见 §三「台账自身也是真源」：每轮入库恰好一个恢复点）。
  台账丢了不是"核对报错"那么简单 —— 备份里那几百个对象会全部显示为 `多出`。

## 四、备份：分母不由工具挑

判据一句话：**分母 = 全库扫描 − 显式声明的可重建集合**。

- 显式可重建集合只有一个地方定义（`_影像备份.mjs` 的 `REBUILDABLE_RE`）：`_crops`、`tiles`、
  `组卷`、`_work-*`、`zzznew`。**新目录默认进分母**——"没被规则命中"不等于"不用备份"。
- `_原图\` 里的对象**按内容全收，不看扩展名**（来源映射 CSV、人工判读 MD 都在里面）。
- 分母必须写进输出。**"我选中的文件都备份好了"这句话永远为真，因此毫无价值。**
- 校验必须**读字节算哈希**，不是比 size、不是比 mtime。
  实测：把一份备份副本改成"同字节数、不同内容"，只比 size 的判据必然判它"一致"。
- 覆盖率不进 100% ⇒ 退出码非 0，**所有模式一套**（`--status` 也要判红，不留"只看不判"的口子）。

## 五、改这个体系时最容易犯的错

| 症状 | 根因 |
|---|---|
| 门禁全绿但原图丢了 | 判据的分母是"我挑的文件"，或校验比的是 size/mtime |
| "删掉对象后工具仍报正常" | 拿台账当"库里现在有什么"，而台账不会因为文件消失而变 |
| 内容被改坏却查不出 | 用 `existing.size === src.size` 判"已存在" |
| 溯源断了但卡片还能显示 | 只更新了卡片引用的路径字段，没同步身份字段（或反过来） |
| 以为备份好了 | 同盘副本当备份；或把快照清单当备份 |

## 六、怎么自己验

```powershell
$env:CTB_DATA='<库根>'
node src\tools\_原图.mjs 校验                          # 逐字节核对全部对象，任一异常 exit 1
node src\tools\_原图.mjs 核对 --from <备份根>            # 备份 ↔ 库 ↔ 台账 三方逐字节对账（只读）
node src\tools\_原图.mjs 快照 --diff <最新清单>          # 有没有对象"非正常消失"
node src\tools\_影像备份.mjs --status                   # 分母 / 已备份 / 缺失
node tests\neg-orig-store.cjs                          # 保全库的 8 组阴性对照（35 断言）
node tests\neg-image-backup-coverage.cjs               # 备份分母的 27 条断言
node tests\neg-orig-restore-drill.cjs                  # 原图恢复演练：4 种情形 + 5 条阴性对照（54 断言）
```

> 上面几条阴性对照是**这条链唯一可信的证明**：它们分别证明了
> "同长度损坏会报红""删掉对象会报红""拒绝覆盖""删除后能回到绿（判据不是恒红）"
> "分母由扫描决定而不是写死"，以及（`neg-orig-restore-drill.cjs`，2026-11-03）
> "换一个全新目录按备份恢复后三方逐字节一致"、"恢复目标坏 1 个字节 / 备份副本坏 1 个字节 /
> 台账字节数被改 / 备份里多出对象 —— 四种都必须判红、还原后必须回到绿"。
> 门禁退出 0 只说明"没触发检查"，不说明"数据安全"。
