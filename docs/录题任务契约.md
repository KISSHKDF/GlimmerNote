# 录题任务契约（任务记录 / 返回信封 / 三层校验 / 候选与修订链）

> 立：2026-11-02（批次 1「任务绑定」）｜引擎：`src\tools\_录题任务.mjs`（唯一读写入口）
> 对应建议书 §4「任务绑定及兼容」。**这份文件是"一次录题到底对应哪张图、哪版配方、哪次任务"的唯一口径。**
> §八（2026-11-03 批次 4）是人工修订的**行为契约**：草案 → 正式写入（引擎 `src\tools\_待确认.mjs`）；
> 字段与目录枚举见 `docs\过程文件规范.md` §六 / §七。

## 一、要解决的问题

页面把任务单交给 AI 之后，程序什么都不留：AI 回传的 JSON 只做格式校验。
于是**把 A 的结果贴进 B** 在程序看来完全合法——卡会挂到错的题上，而且事后无从回溯。
这一类错误必须由程序拦，不能靠人记得。

## 二、任务记录（`<库根>\_录题\<taskId>.json`）

**它是用户数据**（随库走、走 `_安全写.mjs` 原子写），不是过程件：
删掉它就等于删掉"这批卡当时是哪张图、哪版配方产的"。

| 字段 | 说明 |
|---|---|
| `schema` | 固定 `glimmernote.ingest-task/v1` |
| `taskId` | `t-YYYYMMDD-HHmmss-<6位随机>`。**同图同配方再生成仍是两个任务**——否则"错配必须被发现"这条没法验 |
| `createdAt` | 本地时间（带时区偏移） |
| `recipe` | `{id, version, fingerprint}`；`fingerprint` = `_配方.mjs 指纹`（layers + prompt + 反例） |
| `image` | `{sha256, rel}`：原图**完整 sha256** 与库内相对路径。**有 `rel` 必有 `sha256`**——"勾了图却没拿到 sha"的组合在写入口（`createTask`）就被拒（D-4）。记录也允许两者皆空（没指定原图），但那意味着第二层永远未覆盖（见 §四） |
| `subject` / `cards` | 学科；所采用的用户经验卡 `[{packId, cardId, version}]`（批次 2 起才非空） |
| `contractDigest` | sha256(实际拼入正文 + `\0` + `schema.json`) —— **现有"指纹"不含 schema**，故另立一个摘要，专供"这批卡是按哪版契约收的" |
| `taskDigest` | sha256(任务单全文) —— 用来证明"当时给的到底是哪份任务单" |
| `taskText` | 任务单全文（归档；包升级/删除后仍能解释旧任务） |
| `confirmedAt` / `confirmNote` | 第三层：**只由人**跑 `确认` 才写 |

## 三、返回信封（可选，但推荐）

AI 回传允许两种形态：

```jsonc
// ① 有信封（推荐；携带"这是哪个任务"的身份）
{ "envelope": { "schema": "glimmernote.ingest-result/v1",
                "taskId": "t-20261102-214122-fe4219",
                "imageSha256": "<64 hex>" },
  "result": { /* 原业务对象：pageSummary / cards / skipped */ } }

// ② 裸对象（旧格式，仍然收）
{ /* pageSummary / cards / skipped */ }

// ③ 畸形（**拒收**，exit 1）：有 envelope、但形状不对
{ "envelope": { "schema": "glimmernote.ingest-result/v1", "taskId": "…", "imageSha256": "…" } }
//    ↑ 缺 result：外层包了信封，就必须同时给 result
```

**为什么用外层信封**：`cards` 的 schema 设了 `additionalProperties:false`，往里塞 `taskId` 会被拒收；
信封把任务身份放在业务对象之外，**不动**既有契约（建议书 §4 的原话就是这条）。

### 三·一、信封畸形（2026-11-03 补，P1-#2）

判据只有一条：**只要返回的对象里出现 `envelope` 这个键，就必须按信封处置**——不许退回"裸对象"路径。

| 形状 | 处置 |
|---|---|
| `{"envelope":{…}}`（有信封、**缺 `result`**） | 输出「**信封畸形**：返回 JSON 的信封不完整：缺 result（信封必须形如 `{envelope:{…}, result:{…}}`）」，exit **1**（格式层）；`--json` 带 `envelope:'malformed'` + `envelopeError` |
| `{"envelope":"x", …}`（`envelope` 本身不是对象） | 同上，点名「envelope 必须是对象」 |
| `{"envelope":{…},"result":"x"}`（result 不是对象） | 同上，点名「result 必须是对象」 |
| **没有** `envelope` 键的裸对象 | 走上面 ② 的旧路（"仅格式校验"，输出明写「未与任务关联」） |

畸形时第二层记 `not-judged`（**不是** `pass`，也**不是** `not-covered`——后者专指"任务记录缺原图 sha"），
`matched:false`，退出码 1。**为什么不许降级成裸对象**：改前的判据是 `obj.envelope && obj.result`，
于是"有信封、缺 result"被静默降级 ⇒ 外层对象被当业务对象送进格式层，报错变成
「root 缺必填字段「pageSummary」」——用户会以为**自己的 cards 写错了**，而不是漏了 `result` 包装。
指错方向的失败比失败更贵：用户会去改对的东西。

**输入的容错解析（2026-11-03 补，P1-#1）**：AI 回传允许在 JSON 外裹一段说明文字
（「好的，以下是结果：{…} 希望有帮助」）。抽取口径**只此一份**，实现在 `src\tools\_配方.mjs`
的 `extractJsonText`（先原样试，失败才取首个 `{` 到最后一个 `}`；行为**只变宽不变窄**），
`_配方.mjs 校验` 与 `_录题任务.mjs 绑定校验` 共用它，录题页只把用户粘的**原文**原样交出来、
不再自己截花括号。放宽**必须说出口**：人读输出打一行「输入：JSON 外裹了说明文字…」，
`--json` 带 `extracted:'asis'|'braces'`。

## 四、三层校验（`绑定校验 <taskId> --in <file>`）

| 层 | 判据 | 不通过时 |
|---|---|---|
| ① 格式 | 信封畸形先在本工具收口（§三·一：缺 `result` 点名信封+result）；其余交给 `_配方.mjs 校验`（**唯一实现**，界面与 CLI 共用同一份；它自己也会剥信封） | exit **1** |
| ② 与任务及原图匹配 | 信封 `taskId` == 记录 `taskId`；信封 `imageSha256` == 记录图 sha；每张卡 `sourceImageSha256` == 记录图 sha | exit **3**（给具体原因：哪个字段、哪个值、和谁不符） |
| ③ 内容已人工确认 | 记录里的 `confirmedAt`（人跑 `确认` 才写） | **不改退出码**，但输出必须写明"**第三层未完成**"——不许假装全通 |

**第二层是"未覆盖"，不是"通过"（D-4）**：记录没有原图 sha（`image.sha256=null`，例如
`组装 --task` 不带 `--image`，或历史记录）时，第二层**无从核对**。此时输出必须打印
「② **未覆盖**」+ 具体原因，并按**不匹配**处置（exit **3**）——契约对该层是无条件表述，
记录缺 sha 就永远满足不了它。**禁止**"整段跳过却打印 ② 通过"：那是静默假通过，而且方向是
"更宽松 + 更响亮地说通过"（页面把 exit 0 渲染成「✔ 绑定校验通过（① 格式 + ② 与任务及原图匹配）」）。
阴性对照钉在 `tests\neg-task-page-wiring.cjs`（无 sha 任务 + 任意信封 ⇒ 必须 exit 3 且不出现"② 通过"）。

**裸对象（无信封）**：照旧走格式校验，输出明确写"**未与任务关联**"——**兼容不等于把旧结果算成已验证**。

## 五·一、入库（第四步，2026-11-04 新增）

> **为什么有这一步（实测出来的缺陷）**：录题页走完「生成任务单 → 校验 → 人工确认」以前就**结束**了，
> 页面写着「本页不落库」——那句话是**实话**，因为当时仓内**没有任何东西能把 JSON 变成卡**。
> 实测 2026-11-04 19:36 那次录题：任务记录 `t-20261104-193617-a063bc.json` 的 `cards` 是
> **空数组**（校验用的 JSON 只在页面过了一遍，从没存进记录），全库**零张新卡**
> （6295 个文件里当天只被碰了 4 个：1 个派生 `_状态.json` + 2 个任务记录 + 1 张收件箱原图）。
> 用户点完「确认本任务」什么也没发生，界面**也没有任何提示说"没落库"**。
>
> 历史上所有入库都是**仓外一次性脚本**做的（如 `work\kk-math-20261101\land.mjs`），
> 而且那脚本连三道门禁都只是**打印命令让人手跑** ⇒ 落库瞬间 `blindStatus='未盲解'`、
> `answerMode/answerSlots` 缺失，是事后手工补的。**这条链以前不在仓内，就没有门禁管。**

### 五·一·一 命令与退出码

```powershell
node src\tools\_录题入库.mjs 入库 <taskId> --file <cards.json> --student <学生化名> [--subject <学科>]
```

| 码 | 含义 | 典型原因 |
|---|---|---|
| 0 | 入库成功（**或幂等跳过**：同一份内容重跑） | — |
| 1 | 前置不通过 / 门禁未过 | 契约必填字段缺项、`bbox` 越界、门禁报错 |
| 2 | 用法错 / 任务不存在 | 没给 `--student`、学生或学科落点不存在 |
| 3 | 与任务不匹配 | 信封 `taskId`/`imageSha256` 不符、卡的 `sourceImageSha256` 不符 |

**退出码表与 `_录题任务.mjs` 同口径**（0/1/2/3），因为它读的是同一份任务记录、走的是同一套三层。

### 五·一·二 前置条件（缺一不可，程序不替人做）

1. 任务记录存在且**已人工确认**（`confirmedAt` 非空）——**没确认不许入库**。
2. 回传 JSON 的信封 `taskId` / `imageSha256` 与任务记录一致（第二层）。
3. 每张卡的 `sourceImageSha256` 等于任务记录的原图 sha。
4. 学生·学科落点存在（学生的索引里有这一科）。
5. 契约必填字段齐（`subject/title/questionText/studentAnswer/answerSource/causeCode/confidence/sourceImageSha256/teacherAnswer`）。
   ⚠ **`teacherAnswer` 每张卡必填**（2026-11-05）：老师红笔照片上写了正确答案就原样转录，**没写就填空串 `""`**。
   省略它等于让"官方答案悄悄覆盖老师批改"这条检查失明 ⇒ 入库器直接拒收（不限答案来源）。
   配方层 `ingest-page` / `ingest-single` 的 `cards.items.required` 已含该字段。
6. `bbox`（若给了）四个数都在 0~1，且 `x+w ≤ 1`、`y+h ≤ 1`。

任一条不过 ⇒ **零写盘**（不是"写了一半再报错"）。

### 五·一·三 它做什么（**只做这五件事**）

1. 校验上述前置条件；
2. 写卡目录四件套：`题干.html` / `错题记录.md` / `原卷截图.jpg` / `_裁图记录.json`；
3. 往学科 `_索引.json` 的 `items[]` 追加条目（**`answerMode`/`answerSlots` 不在这里写** —— 红线3）；
4. **当场**跑四道门禁（作答契约 / 配图 / 原卷溯源 / 盲解清稿），不留"事后手跑"的欠账；
5. 把 AI 回传的 `cards` **写回任务记录的 `cards[]`**（让"确认"确认的是真东西，不是空盒子），
   并记 `landedAt` / `landedCardIds` / `landedDigest`。

### 五·一·四 幂等

`landedDigest` = 本次入库内容的 sha256（**不含卡号**）。
同一任务、同一份内容重跑 ⇒ 同一个摘要 ⇒ **幂等跳过**（exit 0，打印"已入库过"）。

为什么必须幂等：用户点两次「建卡入库」⇒ 库里两张一样的错题 ⇒ 复习池里同一个错误被算两次
（这正是配方反例 B-07「同一道题拆成两条」要防的后果，只是换了个入口）。

### 五·一·五 落点与边界

- **壳 op**：`ingestLand`（`CTBShellV2.cs` 的 `HostBridge.IngestLand`）。写用户库 ⇒ **进写闸**，
  且放闸**必须挂在 finally 上**（2026-11-04 P0·Critical 同族坑）。
  正文走**临时文件**（cards.json 可能几十 KB，塞 argv 会撞 Windows 32K 上限）。
- **前端**：录题页第 ③ 步校验通过**且已确认**后出现「📥 建卡入库」按钮（`ingest.js` 的 `onLand`）。
  没有任务号、或没带信封 ⇒ **不给按钮**（不能核对归属就不许入库）。
- **坐标口径**：`bbox` 是**归一化 0~1**（`docs\区域契约.md` §三），与该文件同口径。
- **边界**：入库器**不**写 `answerSlots`/`answerMode`（红线3：只能由 `_作答门禁.mjs` 写），
  **不**改写卡正文，**不**碰 `_索引.json` 之外的台账（配图/原卷台账由各自的门禁写）。

## 七、边界（写清，别假装没有）

1. **程序不改 AI 的行为**：任务号只写在任务单第五节 + 要求信封回传；AI 不带信封也能收，只是**无法验证任务归属**（输出里会明说）。
2. **契约真源是本文**。`schema.json` 改版后，旧任务的 `contractDigest` 会与新版不同——这是**特性**（能看出"这批卡是按哪版契约收的"），不是缺陷；需要重放时按 `taskText`（记录里留了全文）重跑。
3. **`数据\_录题\` 是新写入路径**：它**不进** `tests\run.mjs` 的派生白名单（白名单只开 `_状态.json` 与 `_备份-真源\` 两扇门，见 `docs\过程文件规范.md`）。因此**测试一律用副本库**；谁要用真库跑，先想清楚"这轮会不会生成任务"。
4. **壳通道（2026-11-03 接通）**：桌面壳新增两个 op —— `taskCheck`（绑定校验，只读，不进写闸）与 `taskConfirm`（确认，写用户库，进写闸）。taskId 在壳侧有**形状门禁**（`t-8位-6位-6位hex`），参数逐项固定映射、无通用透传（`tests\neg-task-page-wiring.cjs` 钉住）。
5. **带图的任务才有第二层**（D-4，2026-11-03）：`image.sha256` 为空的记录**永远**过不了第二层（输出「② 未覆盖」，exit 3）。这不是"更严"而是"如实"——页面只在勾了照片时才发 `--task`，所以正常录题不会产生这种记录；产生它的只有"没给 `--image` 却要 `--task`"这类用法。要把这种记录变成可校验的，只能重新生成任务单（记录里的 `taskText`/`taskDigest` 保证旧任务仍可解释）。
6. **信封语义只在 `_录题任务.mjs` 判定**（2026-11-03）：`_配方.mjs 校验` 保持"纯格式层"职责，它不判信封畸形——`{envelope:{…}}` 在它那里会被 schema 按"契约外字段 + 缺必填"拒收（exit 1，绝不静默放行），但文案是 schema 层的，不如 §三·一 那样点名。因此**没有任务句柄**时（页面上"只做格式校验"那条路）遇到畸形信封，看到的是 schema 层报错；要走可归因的那一档，先在「2」里勾照片生成任务单、用三层校验。这不是遗漏而是分工：信封是"任务归属"的载体，只有绑定校验知道该拿它跟谁比。
7. **入库只做"落卡"，不做"改卡"**（2026-11-04）：`_录题入库.mjs` 只**新建**卡，不改写既有卡的正文、不删卡、不动复习记录。它也**不**写 `answerSlots`/`answerMode`（红线3：只能由 `_作答门禁.mjs` 写）。要改一张已有的卡，仍走 `_待确认.mjs` 的候选/修订链（§八）——那条链是**人工修订**，与这里的**首次入库**是两件事。
8. **盲解是入库之后的事**：入库后卡面显示 `blindStatus='未盲解'`（这是事实：还没盲解过），
   但入库器会**当场**备好盲解清稿（只有题干，无答案）——材料不能欠账。没盲解的卡进不了组卷池
   （盲解门禁是硬拦），这由 `_标记复习.mjs` 管，不归入库器。

## 八、候选与修订链（人工修订：草案 → 正式写入）

> 立：2026-11-03（批次 4 · 审核与正式入库）｜实现：`src\tools\_待确认.mjs`（`候选` / `修订` / `采用` / `作废候选`）
> 字段与目录的真源枚举在 `docs\过程文件规范.md` §六 / §七；**本节只说行为契约**（子命令、退出码、判据）。

### 八·一 两段式：草案与正式写入分开

| 阶段 | 落点 | 谁能写 | 特点 |
|---|---|---|---|
| 草案 | 条目上的 `candidates[]` | `候选` | 随口提、随时作废；**不进库** |
| 正式写入 | `<库根>\_修订\<kind>\<目标>\<candId>.md` + 条目上的 `revisions[]` | **只有 `采用`** | 进库即用户数据；`revisions[]` 回答"谁在什么时候把哪段正文写进了哪些路径" |

**为什么不直接改写卡正文 / 配方 / 流程文件**：那一步不可逆，而卡正文常是家长自己写的（本仓历史上
"顺手覆盖人工内容"是最贵的一类事故）。本批的验收重点是**幂等 + 可追溯 + 故障后状态一致**，
落点是**新增**的修订对象。"把修订记录应用回卡正文"留作后续单独设计（需单独的批准与回滚口径）。

### 八·二 子命令与退出码

| 子命令 | 语义 | 退出码 |
|---|---|---|
| `候选 --id Txxx --kind 卡\|配方\|流程 --target <卡号/配方id/流程名> --payload "<正文>"` | 建一条草案；打印 `candId` | 0；用法/形状错 2 |
| `候选 … --payload-file <文件>` | 正文从盘上读（**壳走这条**：正文可能上千字，塞 argv 会撞 Windows 32K 上限） | 同上 |
| `修订 --id Txxx [--json]` | 列出候选 + 修订链 + **现值**（只读，一个字节都不写） | 0；条目不存在 / 形状异常 2 |
| `采用 --id Txxx --candidate <candId> [--dry] [--json]` | **正式写入入口**（锁 + 事务） | 0；内容不合法 1；用法/环境错 2；候选不存在或状态不对 3 |
| `作废候选 --id Txxx --candidate <candId>` | 把还没进库的候选标「已作废」（只改 status，不删行） | 0；2；3 |

`--payload` 与 `--payload-file` **互斥**：都不给、都给、或给空正文 ⇒ exit 2，原因具体到是哪一个。
**不许**"看着像路径就当文件读"——正文本身就可能长得像路径。

### 八·三 稳定 ID 与幂等

- `payloadDigest = sha256(正文按 LF 归一后)`（剥 BOM、`\r\n`→`\n`）——
  同一份正文从页面（`\n`）与从 Windows 文件（`\r\n`）进来必须得到**同一个**候选；
- `candId = 'c-' + sha256(kind + '|' + target + payloadDigest) 前 12 位`（单独 `sha256` 的十六进制小写）；
- 同 `kind`+`target`+`payloadDigest` 已存在（且未作废）⇒ **复用**那条 `candId`：打印「已存在，复用」，
  **不新增、不写盘**（连备份都不产生）；
- 已作废的同内容候选再提交 ⇒ 不新增（候选号由内容决定，造不出第二条），**也不改状态**；
  要重新采纳需人工把 `status` 改回「待采用」（工具不替人撤销作废决定）；
- 同一 `candId` 重复 `采用` ⇒ **幂等**：不重复写入、不重复追加 `revisions[]`，exit 0 且打印「已采用（幂等）」。

### 八·四 `采用` 的三类错误（每条都给具体原因，不许一句"参数错"）

正文是**修订包**（JSON 对象）时逐项校验；正文是纯文本（补丁 / 整段替换）时没有机器可读的坐标与页，
**跳过校验并明说**（"正文是纯文本修订……没有坐标/页引用可校验"——不许静默通过）：

| 类 | 判据 | 退出口 |
|---|---|---|
| **越界坐标** | `regions[].{x,y,w,h}` / `origBox` 必须是 **0~1** 且 `w,h>0`、`x+w≤1`、`y+h≤1`；像素 `box` 必须同时给 `imgW`/`imgH`（没有图尺寸就判不了越界，工具不猜），且 `x+w≤imgW`、`y+h≤imgH` | exit 1，报出具体数值与边界 |
| **缺页** | `origPage` 必须是库内相对路径、文件真实存在、且能在 `_页码映射.json` 里查到印刷页；给了 `page` 就必须与它相等。`pageSha` 必须是 64 位小写 hex，且 `_原图\<前2位>\<sha>.<ext>` 在库 | exit 1，报出"哪个值、期望什么" |
| **重复导入** | 落点 `_修订\…\<candId>.md` 已存在：内容**一致** ⇒ 幂等跳过（只补台账）；内容**不同** ⇒ **拒绝覆盖**（人工改过 / 候选号串号，两种可能都要人看） | 一致 0；不同 exit 1 |
| 事务/落盘失败 | 见八·五 | exit 2，且**整体回滚** |

修订包形状（可选；所有字段都可省，省了就不校验那一条）：

```jsonc
{ "note": "可选人话说明",                 // 会被写进 revisions[].note
  "page": 42,                            // 印刷页码（正整数）
  "origPage": "九年级/物理/原卷/整页.jpg",  // 库内相对路径（扫描件）
  "pageSha": "<64 位小写 hex>",
  "origBox": [0.1, 0.2, 0.3, 0.2],        // 0~1 归一化
  "box": [120, 40, 300, 200], "imgW": 1600, "imgH": 1200,   // 证据图像素（必须成对给尺寸）
  "regions": [ { "role": "错误位置", "x": 0.1, "y": 0.2, "w": 0.3, "h": 0.2 } ],
  "text": "整段替换 / 补丁正文（可选）" }
```

### 八·五 锁 + 事务 + 现值

- `采用` 走 `_安全写.mjs` 的**锁 + 事务**：`_修订\…\<candId>.md` 与 `_待确认.json` **一次提交**，
  中途失败**整体回滚**（不留"台账记了修订、正文没落盘"这类半截）；
- 事务里的顺序有意为之：**先写台账留痕、后落正文** —— 这样"正文落盘失败"落在第二个写上，
  回滚必须把台账恢复成原样（阴性对照构造见 `tests\neg-revision-chain.cjs`）；
- `--dry` 只打印"将写什么"，**一个字节都不写**；
- `采用` **绝不**碰 `_索引.json`，因此也绝不直接写 `answerSlots` / `answerMode`（红线 3）：
  真涉及作答契约的修订只能走 `_作答门禁.mjs`，本批的落点不越界；
- **现值**（`修订 --json` 的 `current`）按 kind 给真源，且**必须**带 `presence`（`read` / `missing`）+ `missing` 时的原因：

| kind | 现值 | 定位不到时 |
|---|---|---|
| `卡` | 该卡目录里的 `错题记录.md` 当前全文（卡号优先按各年级/学科 `_索引.json` 的 `items[].id/dir` 定位，目录名兜底） | `current=null`、`currentPresence='missing'`、`currentWhy` 写明"库里没有这个卡号 / 命中多个目录" |
| `配方` | `<AppRoot>\recipes\<id>\prompt.md` 当前全文 | 同上（`currentWhy` 写明程序包里没有 recipes 或没有该配方） |
| `流程` | 没有机器可读的现值 | `currentPresence='missing'`，`currentWhy='流程类目标没有机器可读的现值（人工按修订记录执行）'` |

**不许**把"现值"定义成"最近一条已采用修订的正文"：用户要看的是**现在库里的东西**长什么样，
否则"采用前 vs 采用后"的对照失去意义。

### 八·六 `修订 --json` 的返回形状（界面消费的唯一契约）

```jsonc
{ "ok": true, "id": "T003",
  "candidates": [ { "candId": "c-0123456789ab", "at": "2026-11-03", "kind": "卡", "target": "P0012",
                    "status": "待采用", "adoptedAt": null,
                    "payloadDigest": "<64 hex>", "payloadLen": 17, "payload": "<正文全文>",
                    "summary": "第一行摘要（≤60 字）",
                    "current": "<现值全文或 null>", "currentPresence": "read", "currentWhy": "",
                    "currentFrom": "九年级-学生甲/数学/P0012-示例卡/错题记录.md",
                    "reason": "" } ],                 // 已采用/已作废时写明原因（置灰栏直接用）
  "revisions": [ { "at": "2026-11-03T16:25:46+08:00", "by": "人", "candId": "c-0123456789ab",
                   "kind": "卡", "target": "P0012",
                   "written": ["_修订/卡/P0012/c-0123456789ab.md", "_待确认.json"], "note": "" } ],
  "counts": { "candidates": 1, "pending": 1, "adopted": 0, "void": 0, "revisions": 0 },
  "targets": [ { "kind": "卡", "target": "P0012", "currentPresence": "read", "currentWhy": "",
                 "currentFrom": "…", "current": "<现值全文或 null>",
                 "adoptedCandId": null, "adoptedAt": null } ] }
```

`candidates` 与 `revisions` 都按**台账里的顺序**（append-only ⇒ 时间序）；`targets` 是同一 `kind`+`target`
去重后的现值表（界面左侧栏直接用它，不必自己 cache）。
