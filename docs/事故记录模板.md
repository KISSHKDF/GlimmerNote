# 事故记录模板

> **为什么要模板**：本仓的历史事故**已经**被认真复盘过——但它们散在三种载体里（`CHANGELOG` 的版本条目 = 面向用户、`docs\题干标记-着重号.md` 的"事故现场"节 = 面向某个主题、提交信息 = 面向代码）。
> 结果是：**每次复盘的字段集都不一样**，"这次事故有没有产出改进项"无法机械检查，于是"重大事故必须产出可执行的改进项"这条就只剩习惯。
> 模板的作用不是让人多写字，是让**漏写一项能被看见**。

## 一、什么时候必须写

满足任一条就写：

- 用户数据被**写坏**、被覆盖、或差点被写坏（含"净变化为零但过程危险"）；
- 产物与源码的**对应关系断开**（如历史上那次 `git reset --hard`）；
- 同一类缺陷**复发**（第二次出现即算重大——第一次可以算疏忽，第二次是机制问题）；
- 对外承诺被打破（发布说明、安全时限、`README` 里写下的行为）。

**不写**：单纯的笔误、拼写、措辞；功能迭代中的正常返工。那些进 `CHANGELOG` 就够了。

## 二、模板（复制这段填；一个事故一个文件，放 `docs\事故\`）

```markdown
# <YYYY-MM-DD> <一句话事故名>

## 时间线
| 时刻 | 发生了什么（谁发现的、看到什么） |
|---|---|
| HH:MM | |

## 影响
- **受影响版本/范围**：
- **用户可见后果**：
- **数据侧**（有没有写坏、能否恢复、恢复方式）：

## 根因（机制层，必须指到 文件:行）
- 直接原因：
- **为什么之前没被发现**（这一栏不许写"不小心"）：
- 为什么门禁/测试没拦住：

## 改进项
| # | 类型（门禁 / 文档 / 流程） | 具体动作 | 验收方式（怎么证明它生效） | 状态 |
|---|---|---|---|---|
| 1 | | | | 待落地 / 已落地（文件:行） |

## 复算
（能让人重跑一遍并看到同样结果的命令 + 逐字输出）
```

### 填写要求（有牙齿的部分）

1. **"为什么之前没被发现"必填**。写不出机制，说明还没找到根因——只有"直接原因"的复盘等于没复盘。
2. **改进项必须可执行**。"下次注意"不是改进项；"加一条断言，掏掉它用例必须变红"才是。
3. **改进项要能失败**。门禁类改进项必须附**阴性对照**（把修复掏掉，门禁必须变红），否则无法区分"门禁生效"与"门禁恒绿"。
4. **状态栏要回填**。写成"待落地"就要有人回头改；本仓实测过一类问题：规则标着"待落地"，而它其实早就实现了——**状态字段没人核对，写进去就再没看过**。

### 2026-10-23 「构建脚本被编辑器改成无 BOM，被当成"乱码"处理了两轮」

**时间线**

| 时刻 | 发生了什么 |
|---|---|
| — | 用带自动编码推断的编辑器改 `scripts\*.ps1`，保存成了**无 BOM 的 UTF-8** |
| — | 在 PowerShell 5.1 里跑该脚本：中文注释变乱码、`'`/`"` 配对被打断、`ParseFile` 报假语法错 |
| — | 第一轮判断成了"代码写错了"，去改代码（改错了方向） |
| — | 第二轮才认出是编码问题，把脚本转成 **UTF-16LE** 以让 PS 5.1 正确读取 |

**影响**

- 受影响范围：`scripts\build-release.ps1`、`scripts\deploy.ps1` 两个发布/部署主链路脚本。
- 用户可见后果：当时无（改回了能跑的状态）。
- 数据侧：无。

**根因（机制层）**

- 直接原因：编辑器不保留原有编码；PS 5.1 读**无 BOM** 的 UTF-8 会按 GBK 解码。
- **为什么之前没被发现**：`CONTRIBUTING.md §五` 只写了"`.ps1` 必须 UTF-8 带 BOM"，**没有任何机械检查去核对这句话**——约定只写在文档里，而文档不会在保存文件时拦你。
- 为什么门禁没拦住：`tools\lint.mjs` 只查 JS 的语法/路径/行尾/调试残留，**不看 `.ps1` 的编码**；`git diff --check` 只看行尾空白。

**改进项**

| # | 类型 | 具体动作 | 验收方式 | 状态 |
|---|---|---|---|---|
| 1 | 文档 | `CONTRIBUTING.md §五` 补"违反的表现与自查命令" | 读该节能直接复制出自查命令 | 已落地 |
| 2 | 门禁 | `tools\lint.mjs` 增加**编码断言**（`*.ps1` 必须 UTF-8+BOM；其余文本必须 UTF-8 无 BOM）+ **行尾断言**（与 `.gitattributes` 一致） | 塞一个 UTF-16 文件 / 一个无 BOM 的 `.ps1` 进去，`lint` 必须报红并指出是哪个文件、什么编码 | 已落地（2026-10-29，见 `docs\等级与NA清单.md §五` 第 4 项） |
| 3 | 流程 | 判"脚本报语法错"时**先做编码嗅探**（前 3 字节），再怀疑代码 | 写进本节；下次同类现象第一步就是嗅探 | 已落地 |

**复算**

```powershell
# 前 3 字节是 239,187,191 才是 UTF-8 带 BOM；255,254 = UTF-16LE（本项目应当拒绝）
[System.IO.File]::ReadAllBytes('scripts\build-release.ps1')[0..2] -join ','
# 一眼看全仓：凡是显示 -text 的就是被 git 当成二进制的
git ls-files --eol -- '*.ps1'
```

### 这次实例留下的最重要一条（给下次的自己）

> **"约定写在文档里"和"约定被机械拦住"是两件事。** 本次事件真正的改进不是"改成 UTF-16LE 让它能跑"，而是第 2 项——**让这个错误在提交前就红**。
> 代价也值得记住：当时为了"能跑"选了 UTF-16LE，而这个选择**又埋了第二个坑**（`.gitattributes` 的 `text eol=crlf` 会往 UTF-16 码流里插游离 `0D`，导致**任何人新克隆后这两个脚本都语法错**，而作者本机永远看不见）。
> 教训：**用"绕过检查"修问题，会把问题移到别人看不见的地方。**
